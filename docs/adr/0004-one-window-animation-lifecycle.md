# One window animation lifecycle behind a window port

A window's opening, movement and close are one continuous window animation (see ADR-0003 for where its state lives). A close always continues from the animation's current state, whether mid-opening, mid-settle or idle; each Style decides through a single "begin close" step how its close starts from that state. Each Style has one draw operation. It takes the window's image (the live window buffer while the window is mapped, the retained snapshot once it is gone) and a placement, replacing today's separate live, close and native-close renderers; it also covers a close the Style chooses not to own, where it may still deform Hyprland's native fadeout (liquid does this while its movement settles). A Style declares whether it can draw a dying animation under texture blur; today none of the six can. Where it can't, the animation ends and Hyprland's native fadeout plays. The close renderer becomes only the adapter that draws a dying animation in place of its fadeout.

The window animation module owns monitor and frame rules (which windows step on which monitor, and when) and talks to Hyprland through a narrow window port. The port is a template parameter with two adapters: Hyprland in the plugin and an in-memory fake in tests. That gives frame-sequence tests without a compositor and costs no virtual dispatch. Styles receive only Style-neutral facts (window and screen boxes, neighbour boxes, whether the window is alone, a seed, their own settings), never the runtime or Hyprland window types. Frame-sequence tests drive the module with a test-only Style rather than the real Styles, whose behaviour their model tests already cover.

We rejected continuing a close only when the state happened to be active, keeping separate live and dying draw paths, and a port that merely returned frame outcomes. The last one cannot express re-reading the window's box after a step, which a cloth opening needs. The exact Style interface is chosen separately; it must satisfy these rules.
